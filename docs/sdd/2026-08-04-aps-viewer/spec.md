# Specification: APS Viewer assessment

Status: Approved
Owner: Project owner
Created: 2026-08-04
Last updated: 2026-08-05
Discovery: `discovery.md`

## Problem and outcome

Authenticated users need to configure Autodesk Platform Services (APS) credentials and a Model URN, load an already translated Revit design in APS Viewer, inspect selected model categories, and review a Door and Window quantity report within the existing home experience.

The Model URN is the URL-safe Base64-encoded source design URN whose APS document has an already translated derivative accessible to the configured APS application. It is not a derivative asset URN. The application consumes the existing translation; it does not upload, translate, poll, or manage derivative manifests.

The result must satisfy the original 4–6 hour technical assessment without becoming a production platform. It must provide correct 3D Viewer behavior, deterministic model-derived quantities, graceful failure handling, a working branch or fork, and focused documentation while preserving the base application. Hardening is limited to high-value, proportionate controls for per-user configuration, credential security, asynchronous correctness, Viewer lifecycle, accessibility, testing, and delivery hygiene.

This revision is governed by the project owner's 2026-08-05 specification directives. Where those directives conflict with recommendations in `discovery.md`, this specification is authoritative for Gate 2.

The project owner's 2026-08-05 live-model correction amends category identity narrowly: supported categories are exact direct children of the active model tree root, and their recursive leaf descendants are the element `dbId` values used for coloring and Door/Window counts. The category flow does not read an element property named `Category`.

The project owner's 2026-08-05 quantity-presentation amendment replaces the page-level report with one separate native Viewer extension. Its toolbar command opens a Viewer docking panel whose two collapsible Door and Window sections retain the aggregate result and expose each matched element's public model name and individual Area result when expanded.

## Scope

### Assessment must-haves

- APS Viewer integrated into the existing authenticated home experience.
- APS Client ID, APS Client Secret, and canonical source-design Model URN inputs.
- Backend-mediated APS OAuth and supported Viewer token delivery.
- Exactly one supported 3D viewable from one already translated Revit source design active at a time.
- Native Viewer toolbar toggles for Furniture, Walls, and Doors.
- A Door and Window quantity report derived from the active model at runtime and presented through a separate native Viewer extension.
- Clear loading, empty, partial, unavailable, and failure states for configuration, Viewer, category, count, and Area operations.
- Existing application shell and unrelated behavior preserved.
- A working branch or fork and one focused `ASSESSMENT.md` guide referenced by a minimal appended README link.

### Lightweight production hardening

- One persisted APS configuration per authenticated application user.
- Authenticated encryption for the stored Client Secret using a dedicated environment key.
- No persistent APS access tokens and no Client Secret readback.
- Basic sensitive-data redaction from logs, errors, diagnostics, examples, and source control.
- Atomic configuration-save behavior and distinct configuration-read failure behavior.
- Protection against stale model-load, category, count, and Area-analysis results.
- Stable Viewer runtime ownership for ordinary token renewal and URN-only replacement, with controlled public shutdown and reinitialization only when the persisted credential context changes, without duplicate Viewer instances or toolbar controls.
- Accessible, actionable, non-blocking user feedback.
- Focused automated tests for deterministic and security-sensitive behavior, with manual/live Viewer evidence where appropriate.

## Users and journeys

### Journey 1: Configure and load a model for the first time

1. An authenticated user opens the home experience.
2. A successful configuration read confirms that no configuration exists, so the user sees an explanatory first-time state and inputs for APS Client ID, APS Client Secret, and Model URN.
3. The user enters all three values. Before saving, the application trims Client ID and Model URN, validates the unpadded Base64URL source-design payload and optional single lowercase `urn:` prefix, and shows field-specific guidance for invalid input.
4. Validation, authenticated encryption, and durable per-user persistence complete before the attempted configuration becomes current or model replacement begins.
5. APS Viewer receives access through the backend token callback, the Viewer document identifier is constructed with exactly one leading `urn:` prefix without re-encoding the canonical persisted payload, and one supported 3D viewable loads progressively.
6. Only after the save succeeds is the Client Secret input cleared; later reads show only that a secret is configured.

### Journey 2: Return to, update, or replace the user's configuration

1. An authenticated user returns with a valid saved configuration.
2. A successful read shows the user's saved Client ID, canonical Model URN payload, and configured-secret indicator, then model loading starts automatically.
3. A URN-only save occurs when the normalized Client ID is unchanged and Client Secret is submitted blank. The encrypted secret is retained, the current Viewer runtime and instance are reused, and only model and analysis context are replaced after durable persistence.
4. A credential replacement save occurs when normalized Client ID changes or Client Secret is submitted non-empty, including secret correction or rotation when visible values are otherwise unchanged. A changed normalized Client ID still requires a non-empty Client Secret.
5. After credential replacement is durably persisted, the application invalidates the previous authentication, runtime, model, and analysis context, finishes the owned Viewer, shuts down the global Viewer through the public lifecycle, initializes a new runtime with the supported token callback, creates one new owned Viewer, and loads the persisted Model URN using only the newly persisted credentials.
6. A failed save leaves the prior configuration, Viewer runtime, model, report, toolbar states, matches, and theming unchanged; attempted non-secret values and the secret input remain available for correction or retry.
7. After either successful replacement branch begins, the previous geometry and model-derived state are no longer presented as current, all category toggles reset, and model-dependent controls remain unavailable until replacement data is ready.
8. If credential-context reset, reinitialization, authentication, or loading fails after durable save, the newly persisted non-secret configuration and configured-secret indicator remain editable, the previous model does not return as current, and the Viewer remains explicitly empty or load-failed with actionable retry or reload guidance.
9. No other authenticated user can read or update this user's APS configuration.

### Journey 3: Inspect model categories

1. Furniture, Walls, and Doors controls are owned once by the native Viewer toolbar.
2. Before a usable model and its category data are ready, all three controls are inactive and unavailable for category theming.
3. Successful category resolution makes the affected control usable, including when the successful match count is zero.
4. Each usable control independently toggles a distinct category color and communicates active state without relying on color alone; multiple resolved categories may remain active.
5. A zero-match selection produces the category no-match message. A category-analysis failure instead keeps that control inactive and unavailable, leaves independently resolved controls and geometry usable, and shows an accessible analysis-failure message.
6. Model replacement resets all controls and prevents stale `dbId` values from applying theming.

### Journey 4: Review Door and Window quantities

1. After geometry loads, property analysis proceeds without blocking the usable Viewer.
2. When category and count analysis succeeds, the report presents the deduplicated Door and Window leaf-element counts; zero is a valid successful result meaning no matching elements were found.
3. If category or count analysis fails before a safe count exists, the affected count is unavailable, the affected report result is `failed`, Area is not evaluated or published, and zero is not displayed.
4. After a safe count exists, each matched leaf element contributes at most one unambiguous valid Area value.
5. Area is independently presented as `complete`, `partial`, `unavailable`, or `failed`. Expected missing, invalid, ambiguous, or incompatible data uses `partial` or `unavailable`; only an operational Area-analysis failure uses `failed`.
6. If Area analysis fails after count succeeds, the valid count remains visible, unsafe partial Area results are not published, and only Area is `failed`.
7. Loading another model invalidates every prior match, count, Area result, theming state, and model-specific message.

### Journey 5: Understand and recover from a failure

1. Configuration read, validation, save, authentication, Viewer initialization, APS document loading, category resolution, count analysis, or Area analysis fails while it still affects the active experience.
2. The user receives visible, accessible English feedback explaining what could not be completed and a useful correction or retry action.
3. The existing page shell and unrelated navigation remain usable.
4. Sensitive credentials, tokens, raw APS/OAuth responses, and raw upstream bodies are not exposed in UI, logs, or diagnostics.
5. Expected cancellation or obsolete completion does not publish a stale result or error.

### Journey 6: Deliver the assessment

1. The completed feature is provided in a working Git branch or fork during a later approved delivery gate.
2. Intended implementation files, `ASSESSMENT.md`, and the appended README reference are tracked.
3. Secrets, tokens, environment files, generated database data, and runtime artifacts are excluded.
4. Commit messages and professional submission content are written in English.

## Functional requirements

### Assessment behavior

- `FR-001` — Authenticated home integration: The feature must run inside the existing authenticated home experience and preserve the existing top bar, sidebar, authentication flow, logout behavior, routing, unrelated pages, and unrelated application behavior.
- `FR-002` — Configuration inputs and canonical Model URN: The home experience must provide APS Client ID, APS Client Secret, and Model URN inputs. Client Secret must use password or secret semantics. Client ID and Model URN must be trimmed before validation and persistence; Client ID casing must be preserved. Model URN must represent the URL-safe Base64-encoded source design URN for a source design with an already translated derivative. The user may enter the encoded payload without a prefix or with exactly one lowercase leading `urn:` prefix. After removing that optional prefix, the non-empty payload may contain only `A-Z`, `a-z`, `0-9`, `-`, and `_`; it must contain no `+`, `/`, `=`, embedded whitespace, or another `urn:` prefix. Padding is invalid. The payload must satisfy canonical unpadded Base64URL length and decoding rules, including rejecting a length whose remainder modulo four is one and requiring unused trailing bits in the final Base64URL quantum to be zero. Syntactic validation need not prove APS object existence or translation status. Invalid input must produce field-specific guidance before persistence or loading. The canonical persisted Model URN is the trimmed, unpadded payload without a prefix; equivalent prefixed and unprefixed inputs must not create multiple stored representations.
- `FR-003` — Backend-mediated Viewer access: APS OAuth v2 two-legged token creation must remain on the backend. The Viewer frontend must obtain the short-lived token and its lifetime in seconds only through `getAccessToken(onTokenReady)` during the public `Autodesk.Viewing.Initializer` lifecycle. The callback may obtain a new backend token whenever Viewer requests one and must always use the currently authenticated application user's server-side persisted APS configuration. Ordinary token renewal uses the current runtime. After credential replacement is durably persisted, the old callback and authentication context must be invalidated before public shutdown and a new Initializer callback may obtain tokens only from the new persisted configuration. Obsolete callbacks or tokens must publish nothing. Production Client ID, Client Secret, and Model URN values must come only from persisted configuration. Client Secret must not be returned after save, and production credentials, Model URNs, or fallback identifiers must not be hardcoded.
- `FR-004` — Deterministic 3D model loading and replacement: The application must load the APS document identified by the user's canonical persisted source-design payload, constructing the Viewer document identifier by prepending exactly one `urn:` prefix without encoding or decode/re-encode normalization. It must select the document's default supported 3D geometry viewable when available; otherwise it must select the first supported 3D geometry viewable in deterministic manifest order. It must never silently load a 2D sheet. Absence of a supported 3D viewable is a model-load failure. Exactly one supported 3D viewable may be active. Replacement begins only after a different attempted configuration is durably persisted. Once replacement begins, the previous model must not be presented as the newly current model; replacement failure must leave the new persisted non-secret configuration editable, keep the Viewer empty or load-failed, and never restore the previous model as current.
- `FR-005` — Runtime model data: Furniture, Walls, Doors, and Windows matches and all production Door and Window count and Area values must be derived at runtime from the currently loaded model through supported APS Viewer model and property APIs. Production values must not be hardcoded, precomputed, loaded from fixtures, or supplied by an unrelated backend report. Controlled fixtures and doubles are permitted only in automated tests.
- `FR-006` — Deterministic category matching: Direct children of the active model's public instance-tree root are the only category candidates. Their names must be trimmed and compared case-insensitively using exact matches only, allowing an optional trailing structural count such as ` (11)`. Approved values are `Furniture` and `Revit Furniture`; `Walls` and `Revit Walls`; `Doors` and `Revit Doors`; and `Windows` and `Revit Windows`. Substring matching, fuzzy matching, translated-name guessing, deeper-node category promotion, and element-property category inference are prohibited.
- `FR-007` — Category element identity: Coloring and Door/Window counting must use the unique recursive leaf-descendant `dbId` values beneath an exact supported root category node. Root category nodes, intermediate family/type/container nodes, duplicates, and leaves outside that category subtree are excluded. Model-local `dbId` values must never be reused across models.
- `FR-008` — Native toolbar readiness and category controls: Furniture, Walls, and Doors must each have one labeled, keyboard-operable control owned once by the native Viewer toolbar. Before a usable active model and the affected category data are ready, the control must remain inactive and unavailable for theming. Successful category resolution makes the affected control usable. Each usable category has a distinct color; multiple successfully resolved controls may be active; and turning one off removes only that category's feature-owned theming. Replacement resets all controls to inactive before new category data publishes. No control may theme stale `dbId` values.
- `FR-009` — No-match and category-analysis failure: When category resolution succeeds with zero matches, selecting that usable control must leave it inactive, preserve other category states, and report that no matching elements were found. When category resolution itself fails, the affected control must remain inactive and unavailable, apply no theming, and show an accessible category-analysis failure message; other independently resolved controls and loaded geometry must remain usable.
- `FR-010` — Quantity count states: When category and count analysis succeeds, the report must show the separate deduplicated Door and Window leaf-element count; zero is a valid successful count. If category or count analysis fails before a safe count exists, the affected count must be unavailable, the affected report result must be `failed`, the user must be told that quantity could not be determined, and the usable model must remain available. Area must not be evaluated or published for that affected result. Partial, guessed, cached, or stale counts are prohibited.
- `FR-011` — Deterministic per-element Area contribution: Only a property whose trimmed name is an exact case-insensitive match for `Area` may contribute. Each matched Door or Window leaf element may contribute at most one value. A finite numeric property value is valid when it is zero or positive; negative values, `NaN`, positive or negative infinity, and booleans are invalid. A string is valid only when its entire trimmed content is one finite culture-invariant decimal number. Its grammar is an optional leading `+` or `-`, ASCII digits with at most one `.` decimal separator, and at least one digit overall; exponent notation and grouping separators are not accepted. Parsing must consume the full string, and partial parsing, arbitrary digit extraction, or unrelated text is prohibited. A parsed negative result remains invalid. Area must not be inferred from another property, width, height, dimensions, geometry, bounding boxes, or calculated products. With no exact Area property, the element has missing Area data. With one, that property is validated normally. With multiple exact Area records, they may contribute once only when every exact Area record is valid and all have the same numeric value and normalized unit, with evidence that records from different display categories are duplicates; otherwise the element is ambiguous and contributes no Area. Multiple Area records must never be summed, selected arbitrarily, reduced to a largest/smallest value, or combined across display categories without duplicate proof.
- `FR-012` — Unit normalization, aggregation, and Area states: Unit normalization means trimming surrounding whitespace and preserving the remaining unit string exactly. Case, symbols, notation, language, and scale must not be changed; synonymous notation must not be substituted; missing units must not be inferred. Values are compatible only when every non-empty normalized unit is exactly identical or every valid contribution is unitless. Thus identical `m²` values are compatible, two unitless values are compatible, `m²` differs from `m^2` and `ft²`, unit-bearing differs from unitless, and case-different units are not automatically equivalent. No unit conversion is permitted. After a safe count exists, Area is `complete` only when at least one leaf element matches and every matched element has one unambiguous valid compatible contribution; `partial` when at least one compatible contribution can be summed but one or more matched elements have missing, invalid, or ambiguous Area data; `unavailable` when no safe total exists, including zero matches or incompatible units; and `failed` only when an operational Area analysis failure prevents safe completion after count succeeds. Expected missing, invalid, ambiguous, or incompatible data is not `failed`. An operational failure includes a rejected Viewer/property operation, unreadable property database, premature termination, or unexpected exception. On operational failure, retain count, publish no unsafe subtotal, and mark only Area `failed`.
- `FR-013` — Progressive, generation-scoped state: Geometry loading and property analysis must have visible, non-blocking states. A durably persisted URN-only save advances model and analysis generations while reusing the current runtime and Viewer. A durably persisted credential replacement advances authentication, runtime, model, and analysis generations before controlled runtime replacement. In either branch, previous geometry must cease being presented as current and all previous category matches, toolbar active states, category-dependent toolbar availability, feature theming, Door and Window report states, counts, Area totals, and model-specific feedback must be invalidated. All Furniture, Walls, and Doors controls reset to inactive and remain unavailable until replacement category data is ready. Obsolete callbacks, tokens, runtime promises, models, category, count, Area, errors, or feedback must not update the active experience.
- `FR-014` — Focused assessment documentation: Final delivery must provide one English root `ASSESSMENT.md` covering UI configuration, required environment variables including the encryption key, added dependencies, run and validation steps, Viewer version, supported model and browser assumptions, per-user configuration, architecture/security decisions, development process, known limitations, and relevant troubleshooting. The root `README.md` must retain all existing content and receive only one clearly separated appended link to this guide.

### Lightweight hardening and delivery

- `FR-015` — Per-user configuration read and persistence: Each authenticated application user may read and update only their own MongoDB-persisted APS Client ID, encrypted Client Secret, secret-configured state, and canonical Model URN payload. A successful response explicitly indicating no record exists is the only condition that produces the first-time state. A backend or database read failure must instead show an accessible actionable load error and retry, request no APS token, start no model load, expose no other user's configuration, fabricate no saved values, and leave the shell/navigation usable. First save requires all three inputs. For updates, normalized Client ID is the trimmed case-preserved value; blank Client Secret retains the secret only when that Client ID is unchanged, and a changed normalized Client ID requires a new Client Secret.
- `FR-016` — Secret persistence: Client Secret must use authenticated encryption with a dedicated key supplied through environment configuration. It must never be stored in plaintext or returned by a configuration read. It must be removed from React or other application-controlled browser state only after successful save; a returning user sees only whether a secret exists. Encryption and persistence must fail closed with no partial record.
- `FR-017` — Token lifetime, confidentiality, and storage: Viewer may transiently use only the short-lived APS access token and lifetime required by the supported callback. The token may exist in Viewer runtime memory and required browser network requests but must not be stored in MongoDB, `localStorage`, `sessionStorage`, IndexedDB, application logs, diagnostics, documentation, or long-lived application state. No refresh token is used. Ordinary expiration and callback renewal must not reinitialize the global Viewer runtime. Runtime shutdown and reinitialization are required only after durable credential replacement, not to renew a token.
- `FR-018` — Accessible feedback: Inputs, validation errors, asynchronous status messages, report states, retry actions, and toolbar controls must be keyboard-operable and understandable without relying on color alone. User-impacting failures must be visible, actionable, and specific enough to identify the failed activity and next step without raw APS/OAuth responses or internal implementation details. Blocking browser alert dialogs are prohibited.
- `FR-019` — Viewer lifecycle and authentication-context ownership: At most one global Viewer runtime and one feature-owned Viewer instance may be active. The current runtime and Viewer remain stable across ordinary token expiration/renewal, retry with unchanged credentials, and URN-only replacement. After a durably persisted credential replacement, the application must invalidate prior generations, call `viewer.finish()` on the owned instance, call public `Autodesk.Viewing.shutdown()`, clear feature-owned Viewer references and initialization promises, invoke a new `Autodesk.Viewing.Initializer` with the supported callback, create one new owned Viewer, and load only after reinitialization succeeds. Repeated mount, StrictMode behavior, retry, reset, and teardown must be serialized and idempotent so they create no duplicate runtime, Viewer, callback, listener, or toolbar ownership. Obsolete prior-runtime work must publish nothing. Final ownership release must free feature resources without duplicate shutdown.
- `FR-020` — Assessment-focused Codex skill: A later approved gate must create exactly one concise project-local Codex skill focused on this assessment. It must cover only the repository's existing React, Express, MongoDB/Mongoose, authentication, Tailwind, and UI patterns; serialized Viewer runtime initialization; supported token callback and token-expiration behavior; runtime reuse for renewal and URN-only replacement; controlled public shutdown/reinitialization for credential replacement; Viewer teardown; native toolbar ownership/cleanup; token and Client Secret confidentiality; stale-result prevention; focused testing; scope preservation; and avoidance of unrelated refactors. It must reuse and reference relevant existing repository guidance and must not create a general-purpose framework, extensive skill library, or duplicate generic guidance.
- `FR-021` — Atomic configuration save: Validation must complete before persistence. Encryption and durable persistence must complete before the attempted configuration becomes current or model replacement starts. If encryption or persistence fails, the previous durable configuration, active model, report values, toolbar states, category matches, and theming remain unchanged and associated with that model; attempted values are not represented as saved; non-secret attempted values remain available for correction/retry; Client Secret input is not cleared; and no partial record is persisted. This observable all-or-nothing result does not prescribe transaction infrastructure.
- `FR-022` — Final branch-or-fork delivery: A later approved delivery gate must provide a working Git branch or fork containing the completed feature with all intended implementation files tracked. No Client Secret, encryption key, APS access token, real credential, environment file, generated local database data, dependency directory, or runtime artifact may be committed. Commit messages must be English. Existing README content must remain unchanged, followed only by one link to the tracked English `ASSESSMENT.md` guide. This requirement does not authorize any Git action during Gate 2.
- `FR-023` — Native quantity extension and element detail: The Door and Window report must exist in one feature-owned `Autodesk.Viewing.Extension`, independent from the category-color controls. The extension must own one labeled, keyboard-operable native toolbar command and one resizable Viewer docking panel. The hidden panel leaves the command inactive; opening it makes the command active; closing it through the command or panel close control returns the command to inactive. The panel title is the only visible report heading; an artificial tree root must not be displayed. The panel must contain exactly two initially collapsed, clearly indented root sections, Doors and Windows, with each collapse indicator aligned to its category label. Each collapsed section must expose its category name, safe count state, and total Area state, formatting a valid total to exactly two decimal places without altering the calculated value. Expanding it must list every matched leaf element once, in deterministic category-result order, showing its public model name and its own valid Area value and unit or `Unavailable`. Missing or blank public names must use a deterministic English ordinal fallback without displaying `dbId`. Activating a category or element row must isolate its current-model leaf ids and fit them in view. Closing the panel must clear only isolation applied through this panel and must preserve category theming colors. Individual values must obey `FR-011` and `FR-012`; no additional property, geometry inference, export, or persisted panel/report state is added. Model replacement clears old rows and summaries before new results publish. Extension setup/update/navigation failure must preserve usable geometry, expose actionable feedback, and never publish stale model data.

## Approved technical constraints

- `TC-001` — Viewer version: APS Viewer JavaScript and CSS must use matching exact version `7.118.2` assets. A version change requires an explicit specification decision.
- `TC-002` — APS authorization: APS OAuth v2 two-legged client credentials must be exchanged by the backend using only `viewables:read`. Autodesk user sign-in, consent, callback, refresh-token, Hubs, and ACC browsing flows are excluded.
- `TC-003` — Existing application boundary: Existing application authentication must protect all APS configuration and token operations. MongoDB/Mongoose remains the per-user configuration persistence boundary.
- `TC-004` — Credential cryptography: Client Secret persistence must use authenticated encryption and a dedicated encryption key supplied through environment configuration outside MongoDB and source control.
- `TC-005` — Runtime extraction: Production category, count, and Area values must come from the active model through supported APS Viewer model and property APIs.
- `TC-006` — Serialized Viewer ownership: At most one global Viewer runtime and one feature-owned Viewer instance may support one active 3D viewable. Runtime and Viewer are reused for ordinary token renewal, unchanged-credential retry, and URN-only replacement. A durably persisted credential replacement uses `viewer.finish()`, public `Autodesk.Viewing.shutdown()`, cleared feature references/promises, a new Initializer call, and one new Viewer instance, serialized so old and new runtimes or Viewers are never active together.
- `TC-007` — Supported Viewer token callback: The Viewer frontend must use `getAccessToken(onTokenReady)` during `Autodesk.Viewing.Initializer`. The callback receives the short-lived access token and lifetime seconds in the form Viewer requires, may request a fresh backend token when Viewer asks, and resolves against the authenticated user's persisted configuration for its active runtime generation. No refresh token or runtime reinitialization is used for ordinary token renewal. Credential replacement obtains a new callback only through the public shutdown/reinitialization lifecycle; private token setters, retained-callback invocation, global endpoint mutation, `NOP_VIEWER`, undocumented refresh functions, and a derivative proxy are prohibited.

These constraints protect assessment correctness or credential security. Concrete modules, hooks, services, application route names, file locations, testing libraries, internal manifest/property query algorithms, and the supported model-replacement strategy belong to the Technical Plan.

## Non-functional requirements

- `NFR-001` — Codebase preservation: The implementation must follow existing visual and interaction patterns and reuse suitable existing components, layout primitives, styles, hooks, API utilities, and error patterns. It must not modify a shared component when doing so risks unrelated behavior; a feature-specific component is preferred in that case. The application shell must not be redesigned.
- `NFR-002` — Layout and interaction: Settings, Viewer, feedback, and report must work in the existing application's supported desktop layout in current Chrome and Edge without overlap or interference with the top bar, sidebar, settings controls, report, navigation, or native Viewer toolbar.
- `NFR-003` — Responsiveness and accessibility: Loading and analysis must be progressive and non-blocking. Available UI and loaded geometry must remain usable where the failure contract permits, and status, errors, report meaning, retry actions, and toolbar state must not rely on color alone.
- `NFR-004` — Basic sensitive-data handling: Client Secrets, encryption keys, APS access tokens, Authorization headers, and encrypted secret values must not be written to application logs, diagnostics, error payloads, documentation examples, or source control. Focused security tests must cover feature-owned persistence and response boundaries without requiring a general diagnostic-sanitization or observability framework.
- `NFR-005` — Separation of responsibilities: The implementation must keep per-user configuration persistence, secret encryption/decryption, token acquisition/callback, Viewer runtime/instance lifecycle, model loading/replacement, category/property resolution, toolbar/theming, count/Area analysis, and React presentation/feedback clearly separated. This does not prescribe modules, classes, hooks, services, routes, or folders.
- `NFR-006` — Proportional testability: Focused automated tests must cover high-value deterministic and security-sensitive behavior where practical, especially authorization/per-user isolation, encrypted secret persistence, absence of secret readback, token non-persistence at application-owned boundaries, canonical URN validation, exact root-category matching, leaf `dbId` deduplication, Area contribution/state logic, isolated stale-result protection, and basic Viewer lifecycle ownership/cleanup with controlled doubles. Exhaustive Viewer SDK mocking, automated WebGL rendering, live APS integration in CI, and a production-scale end-to-end suite are not required. Actual rendering, native-toolbar integration, derivative loading, supported 3D selection, and real-model properties may be demonstrated with explicit manual/live evidence. Controlled evidence must not be reported as live; live proof remains open until valid credentials and a representative translated model are available.
- `NFR-007` — Assessment proportionality: Implementation must remain focused on the original 4–6 hour assessment, avoiding speculative abstractions, unrelated refactors, and production-platform mechanisms outside this specification.
- `NFR-008` — Language: All feature-owned repository and professional delivery content introduced by the assessment must be English, including source code and identifiers, tests, comments, UI text, validation/error messages, documentation, commit messages, delivery summaries, and submission content. Pre-existing repository content must not be changed merely to translate it.

## Failure and edge-case behavior

| Situation | Required behavior |
| --- | --- |
| User is unauthenticated | Follow existing authentication behavior and expose no APS configuration or token operation. |
| Successful configuration read reports no record | Show the three inputs and first-time empty state; request no APS token and load no model. |
| Configuration read fails | Do not present first-time/no-configuration state, fabricate values, request a token, or start a model load. Show an accessible actionable configuration-load error and retry while keeping shell/navigation usable and exposing no other user's configuration. |
| First save is incomplete | Identify each missing required field and do not encrypt, persist, or load. |
| Model URN syntax is invalid | Identify the Model URN field and accepted canonical source-design format before persistence/loading; reject padding, invalid alphabet, invalid length/decoding, embedded whitespace, or repeated/non-lowercase prefixes. |
| Client ID changes while Client Secret is blank | Identify that a new Client Secret is required and leave current persistence/model state unchanged. |
| Configuration belongs to another user | Return no values or secret-state information and deny access through existing authentication. |
| Encryption or durable save fails | Preserve prior durable configuration, Viewer runtime, Viewer instance, model, report, toolbar states, matches, and theming; perform no finish, shutdown, or reinitialization; retain attempted non-secret values and Client Secret input; represent nothing as saved; persist no partial record; and show an actionable save failure without cryptographic internals. |
| URN-only save succeeds | Retain the encrypted secret, reuse the current runtime and Viewer instance, advance model/analysis generations, clear prior model-derived state, and replace the model without global shutdown. |
| Credential replacement save succeeds | Persist first, invalidate prior authentication/runtime/model/analysis generations, finish the owned Viewer, call public global shutdown, clear references/promises, initialize a new callback/runtime and Viewer using the newly persisted credentials, then load the persisted Model URN. |
| Credential reset or reinitialization fails after save | Keep the newly persisted non-secret configuration and secret indicator editable, leave Viewer empty/load-failed, publish no prior-runtime callback/token/model/error, do not restore the previous model, and show actionable retry or reload guidance. |
| APS rejects newly saved credentials | Keep new non-secret values and secret indicator editable, keep Viewer empty/load-failed, never restore the previous model as current, and ask the user to verify Client ID/Secret without raw APS/OAuth content. |
| APS or network is temporarily unavailable | Show retry guidance without raw upstream body. No automatic retry loop is required. Obsolete failures must not overwrite a newer successful load. |
| Canonical source-design URN is inaccessible, untranslated, or nonexistent | Keep saved Model URN editable, keep Viewer empty/load-failed without previous model state, and ask the user to verify the canonical source-design URN, completed translation, and APS application access. |
| APS document has no supported 3D viewable | Load no 2D sheet, leave Viewer empty/load-failed, and explain that no supported 3D viewable is available. |
| Viewer assets fail or WebGL/Viewer initialization is unavailable | Retain configuration, keep shell usable, serialize cleanup/retry so no duplicate runtime or Viewer remains, and show an actionable browser/environment message. |
| Replacement begins | Previous geometry is no longer current; reset/disable old-model controls and clear matches, active states, theming, reports, counts, Area totals, and model feedback before replacement data publishes. |
| Replacement fails after save | Keep new saved non-secret configuration/secret indicator editable, leave Viewer empty/load-failed, do not restore previous geometry or derived state, and show correction/retry guidance. |
| Category resolution succeeds with zero matches | Make the affected control usable; selecting it follows no-match behavior and is not analysis failure. |
| Category resolution fails | Keep affected control inactive/unavailable with no theming, show accessible category-analysis failure, and retain usable geometry and other independently resolved controls. |
| Category/count analysis fails before safe count | Keep model usable, show count unavailable and report `failed`, do not display zero, and evaluate/publish no Area total or guessed/cached/stale count. |
| Category/count succeeds with zero matches | Show count `0`, Area `unavailable`, and a non-failed result. |
| Missing, invalid, or ambiguous Area exists | Preserve count; show `partial` if a compatible safe subtotal exists or `unavailable` otherwise. This expected data condition is not `failed`. |
| Area units are incompatible | Preserve count, show Area `unavailable`, and perform no conversion or sum. |
| Area operation fails after safe count | Preserve model/count, publish no unsafe subtotal, and mark only Area `failed`. |
| Obsolete callback/runtime promise/model/token/analysis work completes | Ignore it so prior-runtime activity cannot change active geometry, controls, matches, theming, report, status, or feedback. |
| Viewer ownership is released | Remove feature-owned controls, listeners, theming, references, and resources without a stale post-unmount error, duplicate finish, or duplicate shutdown. |
